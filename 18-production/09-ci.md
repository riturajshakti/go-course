# 18.9 — CI with GitHub Actions

## What You'll Learn

- A complete `ci.yml`: gofmt, vet, build, `go test -race` with coverage, lint, and a Postgres service container
- `go-version-file: go.mod` instead of a hardcoded version, and why that is strictly better
- The shell idiom that makes `gofmt -l` fail the build — demonstrated, because `gofmt -l` **exits 0** on unformatted files
- Least-privilege `permissions:`, a release workflow with cross-compiled artifacts, and the Docker metadata/build-push pair

**No GitHub Actions runner exists in this environment.** Every workflow YAML below is real and
was parsed with `yaml.safe_load`; the run output is labelled as not executed. The Go commands
the workflows invoke **were** run locally, and those outputs are real.

## Coming From Another Language

| Other | Go |
|---|---|
| `npm ci` to install dependencies | nothing to install; `go build` fetches from the module cache |
| cache `node_modules` by lockfile hash | `actions/setup-go@v5` caches `$GOMODCACHE` and the build cache automatically |
| `eslint --max-warnings=0` fails the build | `gofmt -l` exits **0** on failures; you need a shell wrapper |
| `pytest --cov` | `go test -race -coverprofile=coverage.out ./...` |
| a matrix over runtime versions is essential | one Go version is usually fine; the compatibility promise is strong |

## The complete ci.yml

`.github/workflows/ci.yml`, validated as YAML (jobs: `build`, `integration`, `lint`, `matrix`):

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  build:
    name: build and test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
          cache: true

      - name: gofmt
        run: |
          unformatted="$(gofmt -l .)"
          if [ -n "$unformatted" ]; then
            echo "::error::these files are not gofmt'd:"
            echo "$unformatted"
            exit 1
          fi

      - name: go vet
        run: go vet ./...

      - name: build
        run: go build ./...

      - name: test with race detector
        run: go test -race -coverprofile=coverage.out -covermode=atomic ./...

      - name: coverage summary
        run: go tool cover -func=coverage.out | tail -1 | tee -a "$GITHUB_STEP_SUMMARY"

      - uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: coverage.out

  lint:
    name: golangci-lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - uses: golangci/golangci-lint-action@v6
        with:
          version: v1.64.8
          args: --timeout=5m

  integration:
    name: integration tests
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:17-alpine
        env:
          POSTGRES_USER: app
          POSTGRES_PASSWORD: testpassword
          POSTGRES_DB: orders_test
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U app -d orders_test"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
          cache: true
      - name: run integration tests
        env:
          TEST_DATABASE_URL: postgres://app:testpassword@localhost:5432/orders_test?sslmode=disable
        run: go test -tags integration -race -count=1 ./...

  matrix:
    name: go${{ matrix.go }} on ${{ matrix.os }}
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, macos-latest, windows-latest]
        go: ["1.26", "1.27"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: ${{ matrix.go }}
          cache: true
      - run: go test ./...
```

## go-version-file beats a hardcoded version

```yaml
- uses: actions/setup-go@v5
  with:
    go-version-file: go.mod
```

Rather than `go-version: "1.27"`. The reason is that your `go.mod` already declares the
toolchain your code needs, so this is **one source of truth**: bump `go.mod` and CI follows,
with no chance of the two drifting. The failure mode of the hardcoded form is that CI quietly
keeps building with Go 1.24 for a year after everyone's laptop moved to 1.27, so a 1.25
language feature fails only in CI, or worse, a bug that exists only on the old toolchain ships.

`cache: true` is the default in `setup-go@v5` and caches both `$GOMODCACHE` and
`$GOCACHE`, keyed on your `go.sum`. You do not need a separate `actions/cache` step; adding one
usually makes things slower by double-caching. If your repo has several modules, point
`cache-dependency-path` at their `go.sum` files.

## Making gofmt fail the build

`gofmt -l` lists unformatted files and **exits 0 regardless**. Demonstrated for real, with one
badly formatted file in the directory:

```bash
gofmt -l .
echo "exit code of bare 'gofmt -l .': $?"
```

Output:

```
bad.go
exit code of bare 'gofmt -l .': 0
```

So a naive `run: gofmt -l .` step **passes** while printing the problem. Two idioms that
actually fail:

```bash
test -z "$(gofmt -l .)"
```

Output:

```
test -z "$(gofmt -l .)" -> exit=1
```

and the verbose form the workflow above uses, which tells you *which* files:

```bash
unformatted="$(gofmt -l .)"
if [ -n "$unformatted" ]; then
  echo "::error::these files are not gofmt'd:"
  echo "$unformatted"
  exit 1
fi
```

Output:

```
::error::unformatted files:
bad.go
would exit 1: 1
```

After `gofmt -w .`:

Output:

```
test -z "$(gofmt -l .)" -> exit=0
```

Prefer the verbose form: `::error::` is a GitHub Actions workflow command that surfaces the
message as an annotation on the PR, so the author sees it without opening the log. Use
`gofmt -l` rather than `gofmt -d` in CI — the diff is noise when the fix is one command.

`go vet ./...` does exit non-zero on findings, so it needs no wrapper. Note it is also run
automatically by `go test`, but only a subset of its analyzers, so the explicit step is still
worth having.

## The test step

```yaml
- run: go test -race -coverprofile=coverage.out -covermode=atomic ./...
```

`-race` is the single highest-value flag in Go CI ([11.5](../11-sync-context/05-race-detector.md)).
Data races are nondeterministic, so they do not reproduce on your laptop and they do manifest in
production under load; the race detector finds them from a single test execution of the racy
code path. It costs roughly 2-10x runtime and more memory, which is exactly the budget CI has
and your inner loop does not.

`-covermode=atomic` is **required** with `-race` — the default `set` mode uses non-atomic
counter writes, which the race detector would itself flag.

Really run locally, on a small module:

```bash
go test -race -coverprofile=coverage.out -covermode=atomic ./...
go tool cover -func=coverage.out
```

Output:

```
ok  	example.com/scratch	1.498s	coverage: 80.0% of statements
```

```
example.com/scratch/sum.go:3:	Add		100.0%
example.com/scratch/sum.go:5:	Div		100.0%
example.com/scratch/sum.go:12:	Unused		0.0%
total:				(statements)	80.0%
```

The elapsed time varies run to run; the coverage percentages do not.

`go tool cover -func=coverage.out | tail -1 | tee -a "$GITHUB_STEP_SUMMARY"` puts that total on
the job summary page, so the number is visible without downloading an artifact
([14.7](../14-testing/07-examples-coverage.md)). Upload the profile as an artifact and your
reviewers can run `go tool cover -html=coverage.out` locally; push it to Codecov or Coveralls
if you want per-PR diffs, but a coverage *threshold* that fails the build tends to produce
tests written for the metric rather than for the risk.

`-json` emits a machine-readable event stream, which a test-reporter action turns into an
annotated test list:

```bash
go test -json ./... | head -3
```

Output:

```
{"Time":"2026-10-26T14:49:16.323247+05:30","Action":"start","Package":"example.com/scratch"}
{"Time":"2026-10-26T14:49:16.798004+05:30","Action":"run","Package":"example.com/scratch","Test":"TestAdd"}
{"Time":"2026-10-26T14:49:16.7981+05:30","Action":"output","Package":"example.com/scratch","Test":"TestAdd","Output":"=== RUN   TestAdd\n","OutputType":"frame"}
```

Pipe it through `gotestsum --jsonfile` or `dorny/test-reporter@v1` to get a failed-test list as
PR annotations instead of a wall of log text.

## golangci-lint in CI

```yaml
- uses: golangci/golangci-lint-action@v6
  with:
    version: v1.64.8
    args: --timeout=5m
```

`golangci-lint` is not installed in this environment, so nothing was run locally — the YAML
above is nonetheless the correct and current form. It bundles `staticcheck`, `errcheck`,
`govet`, `ineffassign`, `unused` and dozens more behind one binary and one config file
([15.3](../15-tooling/03-linters.md)).

Three details. **Pin `version:`** — an unpinned linter means a new release can fail your build
on an unrelated PR, which erodes trust in CI faster than almost anything else. **Raise
`--timeout`**, because the 1-minute default is not enough for a large module on a cold cache.
And **give it its own job**, so a lint failure and a test failure appear independently rather
than the lint step masking the test results.

Commit a `.golangci.yml` so the laptop and CI run identical rules:

```yaml
linters:
  enable:
    - errcheck
    - govet
    - ineffassign
    - staticcheck
    - unused
    - bodyclose
    - errorlint
    - nilerr
    - rowserrcheck
    - sqlclosecheck
issues:
  exclude-rules:
    - path: _test\.go
      linters: [errcheck]
```

`bodyclose`, `rowserrcheck` and `sqlclosecheck` catch leaked response bodies and `*sql.Rows`,
which are the two leaks a Go service most reliably ships ([17.3](../17-database/03-queries-scanning.md)).

## A Postgres service container

```yaml
services:
  postgres:
    image: postgres:17-alpine
    env:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: testpassword
      POSTGRES_DB: orders_test
    ports:
      - 5432:5432
    options: >-
      --health-cmd "pg_isready -U app -d orders_test"
      --health-interval 5s
      --health-timeout 3s
      --health-retries 10
```

This is the CI half of [17.8](../17-database/08-testing-db.md). The runner starts the container
alongside your job and waits for the health check before running any step — so the
`--health-*` options are not optional decoration. Without them the container is "started" but
Postgres is not yet accepting connections, and your first test fails with
`connection refused` in a way that is intermittent and infuriating.

`ports: - 5432:5432` publishes it on the runner's localhost, so the connection string is
`localhost:5432` (not the service name — that form is for jobs running *inside* a container).

The `-tags integration` build tag keeps these tests out of the fast `build` job
([15.4](../15-tooling/04-build-tags.md)):

```go
//go:build integration

package order_test
```

`-count=1` disables the test result cache, which matters because a cached pass from a previous
commit would otherwise skip tests whose *database* state changed even though the Go code did
not.

## The matrix, and when it is worth it

```yaml
strategy:
  fail-fast: false
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    go: ["1.26", "1.27"]
```

Six jobs. `fail-fast: false` so one failure does not cancel the other five, which is what you
want when you are trying to see *which* combination broke.

Be honest about whether you need it:

| Situation | Matrix? |
|---|---|
| a **library** others import | **yes** — over the two most recent Go versions, since you do not control your consumers' toolchain |
| a CLI people install on their own machines | **yes** over OS; `filepath`, line endings and signals differ |
| a **service** you deploy in your own container | **no** — one Go version and `ubuntu-latest`, matching production exactly |

For the service in this module, the matrix job is the one to delete. You build with one
toolchain into one base image for one OS; testing against Windows tells you nothing and costs
you five job-minutes per push. Go's compatibility promise also means a new minor version almost
never breaks working code, so "test the last two Go versions" buys less for an application than
it does for a library.

## Least-privilege permissions

```yaml
permissions:
  contents: read
```

This is a real security control, not boilerplate. `GITHUB_TOKEN` is minted per job, and on
older repository defaults it has **write** access to contents, issues, pull requests, packages
and more. Any step in your job — including a third-party action you pinned by a mutable tag, or
a transitive dependency of a build tool — runs with that token in its environment and can push
a commit, publish a package or close issues.

Declare the minimum at the **workflow** level and raise it per job only where needed. In
`release.yml` below, the `binaries` job needs `contents: write` to attach release assets and
the `image` job needs `packages: write` to push to GHCR — so each job declares its own, and
neither gets the other's.

While you are there: pin third-party actions, ideally by commit SHA
(`uses: golangci/golangci-lint-action@3a91952...`), because a tag like `@v6` is mutable and a
compromised action with a write token is a supply-chain incident. GitHub's own `actions/*` are
the usual exception people make.

Repository **secrets** (`${{ secrets.FOO }}`) are not available to workflows triggered by
`pull_request` from a fork, by design — so never structure CI so that a required check needs a
secret, or external contributions can never pass. And never `echo` a secret: GitHub masks known
secret values in logs, but not derived ones (a base64 of a secret prints in clear).

## The release workflow

`.github/workflows/release.yml`, validated as YAML (jobs: `binaries`, `image`):

```yaml
name: Release

on:
  push:
    tags: ["v*"]

permissions:
  contents: write
  packages: write
  id-token: write

jobs:
  binaries:
    name: ${{ matrix.goos }}/${{ matrix.goarch }}
    runs-on: ubuntu-latest
    strategy:
      matrix:
        include:
          - goos: linux
            goarch: amd64
          - goos: linux
            goarch: arm64
          - goos: darwin
            goarch: arm64
          - goos: windows
            goarch: amd64
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod

      - name: build
        env:
          CGO_ENABLED: "0"
          GOOS: ${{ matrix.goos }}
          GOARCH: ${{ matrix.goarch }}
        run: |
          VERSION="${GITHUB_REF_NAME#v}"
          COMMIT="$(git rev-parse --short HEAD)"
          BUILD_TIME="$(git log -1 --format=%cI)"
          EXT=""
          if [ "$GOOS" = "windows" ]; then EXT=".exe"; fi
          mkdir -p dist
          go build -trimpath \
            -ldflags="-s -w -X main.version=${VERSION} -X main.commit=${COMMIT} -X main.buildTime=${BUILD_TIME}" \
            -o "dist/server-${GOOS}-${GOARCH}${EXT}" ./cmd/server

      - name: checksums
        run: cd dist && sha256sum * > "SHA256SUMS-${{ matrix.goos }}-${{ matrix.goarch }}.txt"

      - uses: actions/upload-artifact@v4
        with:
          name: server-${{ matrix.goos }}-${{ matrix.goarch }}
          path: dist/*

      - uses: softprops/action-gh-release@v2
        with:
          files: dist/*

  image:
    name: build and push image
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: docker/setup-qemu-action@v3
      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha,format=short

      - uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          build-args: |
            VERSION=${{ github.ref_name }}
            COMMIT=${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

Expected output (runs in CI; not executed in this environment):

```
linux/amd64
  ✓ build                                           11s
  ✓ checksums                                        1s
  ✓ Run softprops/action-gh-release@v2               4s

build and push image
  ✓ Run docker/metadata-action@v5                    1s
      tags: ghcr.io/acme/orders:1.4.2
            ghcr.io/acme/orders:1.4
            ghcr.io/acme/orders:sha-9f3a1c7
  ✓ Run docker/build-push-action@v6                 94s
      #18 exporting manifest list sha256:3c7e...
      #18 pushing manifest for ghcr.io/acme/orders:1.4.2@sha256:3c7e...
```

The parts worth noting:

**`fetch-depth: 0`** is required for `git describe` and `git log` to see the tag and history;
the default shallow clone has neither, and the version injection silently becomes `unknown`.

**`${GITHUB_REF_NAME#v}`** strips the leading `v` from the tag, so `v1.4.2` becomes `1.4.2` —
shell parameter expansion, no extra tool.

**`BUILD_TIME` is the commit's timestamp**, not `date -u`, which keeps the build reproducible
([18.8](08-docker.md)).

**`metadata-action` produces the tag set** from the git ref: `1.4.2`, `1.4` and `sha-9f3a1c7`
from one push, plus OCI labels (`org.opencontainers.image.source`, `.revision`, `.version`)
that make `docker inspect` tell you which commit built the image. Writing those tag rules by
hand is where mistakes like "`:latest` points at a prerelease" come from.

**`cache-from/to: type=gha`** stores BuildKit's layer cache in the Actions cache, so a release
build reuses the `go mod download` layer from previous runs. `mode=max` caches intermediate
stages too, which is what you want for the multi-stage build.

**QEMU plus buildx** is what makes `platforms: linux/amd64,linux/arm64` work on an amd64
runner. Go cross-compiles natively, so the arm64 build is fast despite emulation — only the
base-image layers go through QEMU, not the compiler.

## Required checks and dependabot

Set `build`, `lint` and `integration` as **required status checks** under branch protection on
`main`, with "require branches to be up to date" — otherwise CI is advisory and someone will
merge red.

**Dependabot** (`.github/dependabot.yml`, two ecosystems: `gomod` and `github-actions`) or
Renovate opens PRs for dependency and action updates; the `github-actions` ecosystem is the one
people forget, and it is the one that keeps your pinned action SHAs current.

## Quick Reference

| Step | Command |
|---|---|
| checkout | `actions/checkout@v4` (`fetch-depth: 0` for tags/history) |
| toolchain | `actions/setup-go@v5` with `go-version-file: go.mod` |
| formatting | `test -z "$(gofmt -l .)"` — the bare command exits 0 |
| vet | `go vet ./...` (exits non-zero itself) |
| build | `go build ./...` |
| test | `go test -race -coverprofile=coverage.out -covermode=atomic ./...` |
| coverage total | `go tool cover -func=coverage.out \| tail -1` |
| machine-readable tests | `go test -json ./...` |
| lint | `golangci/golangci-lint-action@v6` with a pinned `version:` |
| integration | `go test -tags integration -count=1 ./...` + a `services:` container |
| release build | `CGO_ENABLED=0 GOOS=.. GOARCH=.. go build -trimpath -ldflags="-s -w -X ..."` |
| image tags | `docker/metadata-action@v5` → `docker/build-push-action@v6` |

| YAML key | Purpose |
|---|---|
| `permissions:` | least privilege for `GITHUB_TOKEN`; start at `contents: read` |
| `concurrency: cancel-in-progress` | kill superseded runs on the same ref |
| `strategy.fail-fast: false` | let every matrix cell report |
| `services.<id>.options --health-*` | the runner waits for readiness before your steps |
| `continue-on-error: true` | a non-blocking step (e.g. a new linter during rollout) |
| `if: github.event_name == 'push'` | skip a job on PRs |

## Common Mistakes

**`run: gofmt -l .` as a check.** It prints the unformatted files and exits 0, so the build
passes; wrap it in `test -z "$(...)"` or an explicit `exit 1`.

**`-race` without `-covermode=atomic`.** The default coverage counters are non-atomic and the
race detector flags them.

**A hardcoded `go-version:`.** CI drifts from `go.mod` and a version-specific bug only appears
in one place; use `go-version-file: go.mod`.

**A service container with no `--health-cmd`.** Tests start before Postgres accepts connections
and fail intermittently.

**Leaving `permissions:` unset.** Every step, including third-party actions, gets a broadly
writable `GITHUB_TOKEN`; declare `contents: read` and raise per job.

**Unpinned third-party actions.** A mutable tag plus a write token is a supply-chain risk, and
an upstream release can break unrelated PRs; pin by SHA, and pin the linter version.

**Shallow clone in a release workflow.** `git describe` and `git log` see no tags, so version
injection silently yields `unknown`; set `fetch-depth: 0`.

**A required check that needs a secret.** Fork PRs cannot access secrets, so external
contributions can never pass.

**Forgetting `-count=1` on integration tests.** The test cache serves a stale pass when only the
database changed.

## Exercises

1. Write the workflow for your own module and get all four jobs green. Then deliberately break
   each gate in turn — an unformatted file, a `go vet` finding, a data race, a lint error — and
   confirm each one fails the build with a useful annotation.
2. Add a job that builds the Docker image from [18.8](08-docker.md) on every PR **without**
   pushing (`push: false`, `load: true`), then runs the image and curls `/healthz`. Make it a
   required check.
3. Replace the plain test step with `gotestsum --format testname --jsonfile tests.json` plus a
   test-reporter action, and compare the PR experience against the raw log on a failing test.
4. Add a `govulncheck` job (`golang.org/x/vuln/cmd/govulncheck ./...`), run it against a module
   with a deliberately old dependency, and capture the real finding. Decide whether it should
   block merges or only warn, and write down why.
5. Make CI enforce the cardinality regression test from [18.7](07-prometheus.md) and the
   secret-redaction test from [18.4](04-service-logging.md) as required checks. Then introduce a
   `user_id` metric label in a PR and show CI rejecting it.
